AppProtectt SDK

Runtime Application Self-Protection that runs inside your mobile app and checks the device and app environment while the app is in use.

Overview

3 questions

AppProtectt is Protectt.ai's Runtime Application Self-Protection (RASP) SDK for mobile apps. You build it into your app. While the app runs, it checks the device and the app environment against the protections configured for your app.

On iOS it comes as an XCFramework with a small set of integration files from Protectt.ai.

RASP (Runtime Application Self-Protection) is security built into the app itself. It watches the app's own environment while the app is running.

Perimeter and server-side controls only see traffic that reaches your servers. RASP works inside the app on the user's device, where risks such as unsafe networks, remote-access tools or screen capture actually happen.

It adds to server-side security, secure coding and code hardening; it doesn't replace them.

Your app runs on devices and networks you don't control. HTTPS protects data in transit, but it can't tell you:

  • whether a remote-access or screen-sharing app is installed
  • whether screens are being captured
  • whether the Wi-Fi network is unsafe
  • whether a request comes from a genuine copy of your app

AppProtectt adds runtime checks for conditions like these. With ATS, it also gives your backend a signal about the device's security state that the backend can verify.

How AppProtectt and ATS work together

1 question

The AppProtectt guide doesn't describe AppProtectt sending threat information to your backend.

For a view of the device's security state that your backend can verify, Protectt.ai provides ATS. ATS creates an encrypted signal, which your backend checks with Protectt's backend plugin to get ALLOW or BLOCK.

In short: AppProtectt protects the app on the device, and ATS lets your server check that protection before it trusts a request.

Security & threat detection

7 questions

The iOS guide documents these protections, depending on what is enabled for your app:

  • Wi-Fi network security validation: checks the security status of the connected Wi-Fi network.
  • Harmful app detection: checks whether certain potentially harmful apps are installed, such as remote-access and screen-sharing tools.
  • Screenshot prevention: blocks screenshots of the app's screens.
  • App attestation: uses Apple's App Attest to help confirm the app is genuine. Applies only if this rule is in your threat model.
  • Device association: links the SDK to a device identifier you provide.
Pending confirmationThe guide doesn't list the full set of runtime detections (for example jailbreak, debugger, hooking or tampering detection). Protectt.ai should provide the complete coverage for your configuration.

Protections are set per customer. Protectt.ai supplies a Threat Modelling document and a Release Document for your app, and some integration steps depend on them.

For example, App Attestation is only needed if the attestation rule is in your threat-modelling sheet. You also get separate feature files for UAT and production.

iOS requires location permission before an app can read details of the connected Wi-Fi network. AppProtectt needs those details for Wi-Fi security validation.

The guide gives suggested permission text saying location is used only to check the network's security. If your app already asks for location permission, you can keep your existing text.

Pending confirmationWhat AppProtectt does if the user denies location permission.

iOS only lets an app check whether another app is installed if that app's URL scheme is declared in Info.plist, under LSApplicationQueriesSchemes. Protectt.ai provides the list of schemes AppProtectt uses for harmful-app detection.

If your app already has this key, add the provided entries rather than replacing yours. iOS limits how many schemes an app can declare, so check the combined total if you already declare many.

It blocks screenshots of your app's screens. You turn it on once, passing the app's window, either in your base view controller or in AppDelegate right after starting the SDK.

Pending confirmationWhether it also covers screen recording and screen mirroring, and the recommended setup for apps that use SceneDelegate.

App Attest is an Apple service that helps a backend confirm that requests come from a genuine copy of your app on a genuine Apple device. You only need it if the attestation rule is in your threat model.

Setup has two parts:

  • Apple Developer Portal: create an App Attest key and enable the App Attest capability. The key file can only be downloaded once, so store it securely.
  • Xcode: add the App Attest capability and set the App Attest environment entitlement to production.
Pending confirmationHow the App Attest key and Key ID are shared with Protectt.ai, and what happens on devices or iOS versions that don't support App Attest.

No protection that runs on the device can be guaranteed against a determined attacker, because the attacker controls the device. ATS is designed to close this gap.

With ATS, your backend requires a valid, encrypted signal tied to the session. A missing, invalid or tampered signal, or unusual device parameters, results in BLOCK on the server. So tampering can be detected even if the on-device checks are defeated.

Where App Attest is enabled, it adds another check that the app is genuine.

Pending confirmationWhat measures AppProtectt uses to protect itself against tampering.

Mobile integration (iOS)

6 questions

The iOS guide specifies:

  • iOS 12.0 minimum deployment target (iOS 14.0 if you also use ATS)
  • Xcode 15.0 or later
  • Swift 5.5.2 or later
  • Swift and Objective-C projects are both supported

You also need an Apple Developer account to:

  • add capabilities (Access Wi-Fi Information, Hotspot, and optionally App Attest)
  • regenerate provisioning profiles if needed
  • supply your Apple Team ID
Pending confirmationAndroid and cross-platform frameworks (Flutter, React Native, .NET MAUI/Xamarin) aren't covered by the documents reviewed.

For each environment you get a Release Document. It holds your app-specific settings and credentials (Client ID, Channel ID, licence details) and download links for the SDK, feature file, integration guide, handler file and Threat Modelling document.

A typical iOS integration:

  1. Add the SDK framework, handler file, alert UI files, icon assets and feature files to your app target.
  2. Set the framework to "Embed & Sign".
  3. Start the SDK when the app launches.
  4. Add the required capabilities and Info.plist entries: location permission for Wi-Fi validation, and queried URL schemes for harmful-app detection.
  5. Pass a device ID to the SDK.
  6. Turn on screenshot prevention.
  7. Turn on App Attest, if your threat model includes it.
  8. Optionally, add ATS so your backend can verify threat signals.

The documented changes mostly add files and configuration:

  • adding files
  • a few SDK calls (start-up, device ID, screenshot prevention)
  • Info.plist entries and capabilities
  • possibly regenerated provisioning profiles

The guide doesn't call for changes to your business logic. If your app already asks for location permission or already declares queried URL schemes, you add to that configuration rather than replacing it.

You start the SDK when the app launches, in AppDelegate's didFinishLaunchingWithOptions, using the values from your Release Document plus your Apple Team ID.

A build-flavour setting picks the environment: development/UAT or production. Each environment has its own feature file and credentials, so make sure production builds use the production values.

The device ID ties the SDK session to the current device. You can use your existing way of identifying devices; the guide's example uses the iOS vendor identifier.

Use a stable identifier, and use the same one across your app and backend.

Pending confirmationWhether the device ID given to AppProtectt must match the one given to ATS.

The handler file is the layer between your code and the SDK. Your app calls it to start AppProtectt, pass the device ID and turn on screenshot prevention.

Use the handler file from the same release as the SDK.

Pending confirmationWhether the handler offers callbacks or events your app can subscribe to (for example, to learn which threat was detected), and whether customers may modify it.

Overview

2 questions

ATS is Protectt.ai's threat-signal SDK. It sits alongside AppProtectt in your mobile app and creates a signal token: an encrypted summary of the device's security state, tied to a session. Your app sends the token to your backend, where Protectt's Java plugin checks it and returns ALLOW or BLOCK.

The solution has three parts:

  • the ATS SDK in the app
  • the Threat Signal Validation Plugin (a JAR) in your backend
  • Protectt.ai's server, which the plugin consults for extra checks such as whether the device is blacklisted

AppProtectt protects the app on the device. But from a normal API request, your backend has no way to tell whether that protection is present and working. An attacker could reverse-engineer the app, tamper with the SDK or remove it, and then call your APIs directly.

ATS moves the trust decision to your server. Each protected request must carry a valid signal, tied to a session and a timestamp, which your backend decrypts and checks through the plugin. If the signal is missing, tampered with, too old, or reports problems, your backend can block the request.

This makes it much harder to get around the on-device protection unnoticed, though no control can guarantee protection against every attack.

How AppProtectt and ATS work together

3 questions

ATS is added to the same project as AppProtectt. The signal it creates includes threat parameters describing the device's security state, plus session and device identifiers.

Pending confirmation
  • How ATS gets security results from AppProtectt (for example, through a handler callback).
  • Whether creating a signal depends on AppProtectt having finished its checks.

The documented inputs are:

  • Session ID, issued by your backend
  • Device ID, a unique identifier for the device
  • Timestamp, generated by your server

The token is encrypted. It carries the session ID, a Protectt device identifier ("pbid"), the device ID, threat parameters and the session timestamp.

Your app doesn't need to read or build the token; it just passes it on. To see what a decrypted token contains, try the Threat Signal Decoder.

The plugin returns its result to your backend, not to the app. Your backend enforces the decision and chooses what to send back in the API response.

For example, it can continue on ALLOW, or on BLOCK return an error or blocked status so the app can tell the user. The docs describe the final JSON (action, reason, code, identifiers and timestamp) as being returned to the frontend.

Mobile integration (iOS)

2 questions

  1. Add the ATS SDK package (ATS.xcframework) to the same project as AppProtectt and set it to "Embed & Sign".
  2. Set your app's minimum deployment target to iOS 14.0 or later.
  3. Get a session ID and a timestamp from your backend.
  4. Call ATS's signal method with the session ID, a unique device ID and the timestamp.
  5. Send the returned signal token to your backend in the request body.

Put it in the JSON body of each API request you want to protect:

  • signalToken: the encrypted signal (required)
  • clientSessionID: the session ID the signal was created for
  • clientId and chnId: your client and channel identifiers

You choose which APIs carry the signal; the docs mention onboarding and transaction flows. A request with a missing or invalid signal is treated as invalid and returns BLOCK.

Backend integration & API

3 questions

The Threat Signal Validation Plugin is a small Java library you add to your backend. For each signal from the app, it:

  1. checks the required fields are present
  2. decrypts and decodes the token
  3. makes a first decision
  4. asks Protectt.ai's server for extra checks, such as blacklist status
  5. returns a final ALLOW or BLOCK with a reason code

You don't write any decryption or threat-checking logic yourself.

Decryption happens inside the plugin, using a private key your backend passes to the validation call. Treat this key as a secret.

A token that can't be decrypted, or has been changed, results in BLOCK (P001). After its own checks, the plugin sends the decoded signal to Protectt.ai's server for more checks and combines both results.

Decisions & response codes

5 questions

The verdict combines two things: the plugin's own checks on the token (integrity, session match, device parameters) and checks on Protectt.ai's server (for example, blacklist status).

CodeActionMeaning
P000ALLOWValid device and environment
P006ALLOWValid device and environment, with a locally generated device identifier
P001BLOCKInvalid or tampered signal token
P002BLOCKUnexpected error during validation
P003BLOCKProtectt server rejected validation
P004BLOCKAnomalies in device parameters (rule bypass detected); includes the rule IDs triggered
P005BLOCKDevice already blacklisted
P007BLOCKSession ID mismatch

Each result has action, reason and code, plus pbid, sessionId, deviceId and timestamp where they apply. To see a decrypted response for a real token, use the Threat Signal Decoder.

Required by the docs

  1. Match the session. Check that the returned sessionId matches the session you stored.
  2. Check freshness. Check that the returned timestamp is within your allowed window (for example, 5 minutes).
  3. Enforce the action. Continue the business request only on ALLOW; reject it on BLOCK.

Recommended

  • Log the result. Record the code, reason and any rule IDs for monitoring and investigation.
Pending confirmationRecommended handling of P006 (ALLOW with a locally generated device identifier).

The session ID ties the signal to a specific session your backend issued. If the session doesn't match, the plugin returns BLOCK with code P007 ("SessionId Mismatch").

Your backend must also confirm that the sessionId in the result matches the session it stored for that user or request. This stops a signal from one session being reused in another.

Pending confirmationThe required session ID format and length. The samples show different lengths.

The device ID identifies the device that sent the signal. It comes back in the result along with Protectt's own device identifier (pbid), which allows decisions per device, such as blacklisting.

Use a stable, unique identifier.

Pending confirmationWhether it must be the same device ID given to AppProtectt, and how app reinstalls or identifier resets are handled.

The timestamp lets your backend confirm that a signal is fresh, not a replay of an earlier recorded request. After validation, compare the returned timestamp with your server's current time and reject signals outside your allowed window. The docs' example is about 5 minutes.

Using a server timestamp avoids relying on the device's clock, which a user or attacker can change.

Failure & fallback scenarios

3 questions

The protection comes from your backend enforcing the check. As long as your backend requires a valid signal on protected APIs:

  • No token is sent (for example, ATS was removed or the call was skipped): the request is invalid and returns BLOCK (P001).
  • The token is changed or forged: it fails the check and returns BLOCK (P001).
  • An old token, or one from another session, is replayed: the session-mismatch check (P007) and your own session and freshness checks catch it.
  • Device parameters show anomalies or a rule bypass: the result is BLOCK (P004), with the rule IDs triggered.

These protections only work if your backend rejects every protected request that doesn't have a valid ALLOW.

Pending confirmationWhat ATS produces when AppProtectt is missing, not started, or hasn't reported results. In particular, whether ATS creates a signal that comes back as BLOCK, or fails to create one at all.

The documented results are:

  • BLOCK for unexpected errors during validation (P002)
  • BLOCK when Protectt.ai's server rejects validation (P003)

The sample code also shows that parsing or connection problems can come through as exceptions, which your code must handle. Decide how to handle these cases and apply it consistently. For high-risk operations, the usual choice is to fail closed (block).

Pending confirmation
  • Timeout and retry behaviour.
  • Whether an unreachable server returns P002 or throws an exception.
  • Whether any fail-open option exists.

According to the docs, when Protectt.ai's server returns BLOCK, the device is blocked and blacklisted. Later checks from that device return BLOCK with code P005 ("Device already blacklisted").
